# AI大玩家版本发布流程

整理日期：2026-10-06。本文依据当前仓库配置，说明 GitHub 发版与生产上线的先后顺序；编写本文没有提交代码、创建标签或更新服务器。

同日已按本文完成首次自有版本的发布与生产切换，具体结果和待补验收项见 [v1.0.0 发布记录](releases/v1.0.0.zh.md)。

服务器部署结构、数据库连接和配置路径见[生产环境部署](README.zh.md)。服务器状态沿用已有部署记录，发布前需要重新核对。

## 1. 当前具备的流程

- 自有仓库：`peicc-TheChosenOne/dujiao-next-cc`；部署分支：`codex/deploy-aiccpay`。
- 推送 `v*` 标签会触发[发布工作流](../.github/workflows/release.yml)，由 [GoReleaser](../.goreleaser.yaml) 构建包含前后台的多平台二进制并创建 GitHub Release。首次使用需确认仓库 Actions 已启用，最终以任务成功和产物检查为准。
- 当前发布工作流没有测试步骤，也不会发布 Docker 镜像或自动更新服务器。
- [CI](../.github/workflows/ci.yml) 的普通 push 覆盖 `main/dev/codex/deploy-aiccpay`，PR 也会触发检查。
- 现有生产部署采用指定提交的源码快照构建 Docker 镜像，服务器 `.env` 的 `APP_IMAGE` 固定本地镜像 ID。
- 后台“检查更新”仍读取上游 `dujiao-next/dujiao-next`，不能作为自有版本的发布入口。

完整顺序：审核改动 → 验证 → 提交并推送 → 打标签 → 检查 Release → 准备应用镜像 → 备份 → 切换应用 → 验收并记录。

## 2. 审核、验证并提交

1. 确认本次包含哪些功能、修复和品牌清理，检查待提交差异。未提交的改动不会进入标签及发布产物。
2. 只提交审核过的源码和文档；不提交运行配置、密码、私钥、数据库数据或临时输出。
3. 完成与改动相关的 Go 测试、前后台测试及 fullstack 构建，验证后台登录、分类保存、客服字段等受影响功能。
4. 通过 PR 运行 CI，或先补充部署分支的 CI 触发条件。已有局部测试通过不能替代最终发布提交的验证；发布任务只打包，不负责拦截测试失败。
5. 提交并推送最终代码，记录完整提交号。发布标签必须指向通过检查的提交。

## 3. 确定版本并创建标签

下面以 `v1.0.0` 为示例，实际版本先检查远端标签，避免与已发布版本重复。版本修复可递增为 `v1.0.1`，新增功能可递增为 `v1.1.0`。

在本地仓库执行，确认当前 HEAD 就是本次发布提交后再打标签：

```bash
git ls-remote --tags origin
git rev-parse HEAD
git tag -a v1.0.0 -m "AI大玩家 v1.0.0"
git push origin v1.0.0
```

在 GitHub Actions 中确认发布任务成功，再检查 Release 的版本、说明和下载文件。已发布标签不再移动，后续修复使用新版本号。

当前 Release 说明指向自有部署文档，安装脚本的发布 API、下载校验及脚本来源均使用自有仓库。安装脚本用于独立二进制安装，不用于更新现有 Compose 部署。

## 4. 按现有方式准备 Docker 镜像

GitHub Release 的二进制发布和 Docker 镜像部署是两个步骤。现有 Dockerfile 会重新构建两套前端并嵌入 Go 应用，不会自动使用 Release 附件。

在与发布标签对应的干净源码快照根目录构建；以下命令在 Linux Docker 构建环境执行，版本号与标签保持一致：

```bash
docker build --build-arg APP_VERSION=v1.0.0 --tag dujiao-next:v1.0.0 .
docker image inspect dujiao-next:v1.0.0 --format '{{.Id}}'
```

当前方案要求该镜像已存在于生产服务器的 Docker 中。若在其他机器构建，需构建与服务器架构匹配的 Linux 镜像，并通过镜像仓库或导出/导入方式送到服务器，再取得服务器上的镜像 ID。

2 核 / 4 GB 服务器构建前后台会占用额外资源，优先在构建机准备镜像；先完成构建，再开始线上切换。旧应用镜像保留到验收完成及回滚保留期结束。

## 5. 备份并切换应用

在服务器执行：

```bash
cd /opt/dujiao-next
./backup.sh
```

确认备份成功、记录备份路径和旧的 `APP_IMAGE` 后，再进行以下修改：

- 只修改 `.env` 中的 `APP_IMAGE`，填写新镜像 ID；保留数据库镜像、Redis 镜像及 `COMPOSE_FILE` 等原有字段。
- 核对新版本需要的配置。本次 TOTP 品牌修改需将 `config/config.yml` 的 `app.totp_issuer` 同步为 `AI大玩家`；保留原有加密密钥和认证凭证。
- 更新应用容器：

```bash
docker compose up -d --no-deps --wait --wait-timeout 180 app
curl --fail http://127.0.0.1:8080/health
docker compose logs --tail=100 app
```

此步骤只更新应用；PostgreSQL、Redis 和数据目录沿用现有部署。配置修改发生在备份之后，便于恢复原配置。网站证书和 Nginx 反代一般无需随应用版本重新配置。

## 6. 验收与发布记录

- 检查应用健康状态、启动日志、数据库迁移及 Redis 连接。
- 访问 `https://aiccpay.com` 和既有后台安全入口，确认页面及静态资源加载正常，应用版本正确。
- 验证后台登录、分类保存、品牌、客服以及本次修改影响的功能。SMTP 已配置时检查测试邮件；TOTP 名称仅影响新绑定，已有验证器标签不会自动改名，无需重新绑定。
- 按已配置业务验证下单、支付回调、自动发货及人工交付，避免重复发送交付内容。
- 更新服务器 `/opt/dujiao-next/deployed.json` 中的版本、完整提交号和镜像信息；同时记录发布时间、备份路径及验收结果。该文件需要发布执行者更新，Compose 不会自动维护它。

## 7. 回滚

应用回滚时，把 `.env` 的 `APP_IMAGE` 恢复为记录的旧镜像 ID，并恢复本次需要回退的应用配置，再执行：

```bash
cd /opt/dujiao-next
docker compose up -d --no-deps --wait --wait-timeout 180 app
curl --fail http://127.0.0.1:8080/health
```

回滚前确认数据库迁移与旧版本兼容；若不兼容，需要停写并结合备份恢复，不能只换镜像。恢复数据库会影响备份后的订单和其他新增数据，需要先核对这些变化。回滚完成后同步发布记录。

## 8. 后续建议：GitHub 构建镜像，服务器仅拉取

这部分尚未实施，需要补充工作流后才能使用：

1. 部署分支已增加 CI；发布前仍需确认目标提交的测试和构建全部通过。
2. 标签触发 Docker 镜像构建并推送 GHCR，写入同一版本号和提交标识。
3. 服务器完成镜像仓库认证后，以 `ghcr.io/...@sha256:...` 的固定仓库摘要填写 `APP_IMAGE`；它与当前使用的本地镜像 ID 含义不同。
4. 按第 5 节备份后，修改 `APP_IMAGE`，先执行 `docker compose pull app`，成功后再切换应用并验收。

当前本地镜像 ID 方案不需要执行 `docker compose pull app`。GHCR 接入后才使用远程拉取流程；第一次接入须保留旧镜像 ID，便于回滚。上游更新入口是否调整属于另一项源码工作，不会因创建自有 Release 自动切换。
