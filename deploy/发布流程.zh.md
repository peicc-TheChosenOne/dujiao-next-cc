# 版本发布与部署流程

本文件说明通用流程。实际服务器、发布提交、镜像摘要、备份位置和验收结果只记录在仓库外的私有运维目录。

## 发布前

1. 开发分支为 `codex/dev`，生产分支为 `codex/deploy-aiccpay`。按功能审核并提交，检查没有夹带运行配置、密钥、真实数据或运维记录。运行配置分别留在开发机和服务器，分支之间只合并代码及示例配置。
2. 按 `AGENTS.md` 执行与改动范围对应的测试和构建，全部通过后再合并。
3. 检查数据库迁移及业务规则变化，明确升级影响和回滚条件。
4. 合并并推送生产分支。创建版本标签前确认标签对应的提交正确。

提交前执行 `python3 scripts/check-release-safety.py`。CI 会检查配置与数据文件、私有运维目录、部署模板中的公网 IP 和发布包文件白名单。该检查也在 GoReleaser 构建开始前运行。真实地址和密码放入忽略的 `config.private.yml`，不要放入 `VITE_*` 环境变量，它们可能出现在公开前端 JavaScript 中。

## GitHub 发布

1. 为已合并到生产分支的提交创建 `v主版本.次版本.修订版本` 标签并推送。发布工作流校验标签及其生产分支归属，并重新执行完整 CI；任何检查失败都会阻止发布。
2. 确认 CI 和发布工作流通过，核对各平台归档及 SHA256 校验清单。
3. 发布说明只包含功能变化、兼容性和公开安装信息；不包含实际服务器配置和部署记录。
4. 当前归档白名单只包含程序、根目录 README、`config.yml.example`、`config.private.yml.example` 和安装脚本。私有运维资料不得加入发布包。本地检查归档时执行 `python3 scripts/check-release-safety.py --archives dist`。

## 部署与验收

1. 保存当前镜像和运行配置，在仓库外记录回滚所需信息。
2. 备份数据库、Redis、上传文件、配置及密钥，验证备份能够恢复。
3. 从发布标签的干净源码构建应用镜像，核对版本并固定镜像标识。
   构建上下文通过 `.dockerignore` 排除私有配置、环境变量、运维记录、运行数据和宿主机构建产物；镜像只包含二进制及脱敏配置模板。
4. 使用服务器自己的运行配置更新应用容器：

   ```bash
   docker compose up -d --no-deps app
   docker compose ps
   docker compose logs --tail=100 app
   ```

5. 检查健康接口、前后台页面、鉴权、商品及订单流程、后台任务和日志；资金及发货流程根据测试条件验收。
6. 将验收结果、备份位置、镜像标识和回滚条件保存在私有运维目录。

升级期间保留服务器上的普通配置、私有配置和 PostgreSQL/Redis 密码文件。新程序需要配置变更时单独调整并验证，不用开发机配置覆盖服务器，也不把密钥放入版本标签、发布说明或构建参数。加密密钥必须与数据一同备份；禁止将私有备份上传为 GitHub Release 附件。

## 回滚

如果数据库结构与旧程序兼容，可恢复旧应用镜像；如不兼容，须评估数据库和业务数据的恢复方案。运行中的新订单、支付及交付数据必须纳入评估，不可机械恢复旧备份。

回滚命令和校验应依据实际环境准备、演练，并保存在私有运维目录。
