# 版本发布与部署流程

本文件说明通用流程。实际服务器、发布提交、镜像摘要、备份位置和验收结果只记录在仓库外的私有运维目录。

## 发布前

1. 确认开发分支、生产分支、待发布内容及版本号，检查没有夹带运行配置、密钥、真实数据或运维记录。
2. 按 `AGENTS.md` 执行与改动范围对应的测试和构建，全部通过后再合并。
3. 检查数据库迁移及业务规则变化，明确升级影响和回滚条件。
4. 合并并推送生产分支。创建版本标签前确认标签对应的提交正确。

## GitHub 发布

1. 为审核通过的提交创建版本标签并推送。`v*` 标签触发发布工作流。
2. 确认 CI 和发布工作流通过，核对各平台归档及 SHA256 校验清单。
3. 发布说明只包含功能变化、兼容性和公开安装信息；不包含实际服务器配置和部署记录。
4. 当前归档配置包含程序、根目录 README、示例配置和安装脚本。私有运维资料不得加入发布包。

## 部署与验收

1. 保存当前镜像和运行配置，在仓库外记录回滚所需信息。
2. 备份数据库、Redis、上传文件、配置及密钥，验证备份能够恢复。
3. 从发布标签的干净源码构建应用镜像，核对版本并固定镜像标识。
4. 使用服务器自己的运行配置更新应用容器：

   ```bash
   docker compose up -d --no-deps app
   docker compose ps
   docker compose logs --tail=100 app
   ```

5. 检查健康接口、前后台页面、鉴权、商品及订单流程、后台任务和日志；资金及发货流程根据测试条件验收。
6. 将验收结果、备份位置、镜像标识和回滚条件保存在私有运维目录。

## 回滚

如果数据库结构与旧程序兼容，可恢复旧应用镜像；如不兼容，须评估数据库和业务数据的恢复方案。运行中的新订单、支付及交付数据必须纳入评估，不可机械恢复旧备份。

回滚命令和校验应依据实际环境准备、演练，并保存在私有运维目录。
